## 1. Why LeRobot?

[LeRobot](https://github.com/huggingface/lerobot) is an open-source library and
dataset ecosystem for robot learning. It provides:

- a standard dataset format (v3 at the time of writing) with Parquet metadata and
  MP4 video;
- loaders that return PyTorch tensors and handle episode boundaries;
- reference implementations of ACT, Diffusion Policy and other policies;
- hardware integrations for low-cost arms such as SO-101;
- a Hub of public datasets.

You do **not** need LeRobot to complete this tutorial. The value is in comparing
your implementation with a mature one, and in using real demonstrations that were
not generated by your own scripted controller.

> **Version warning.** LeRobot evolves quickly. The APIs below are based on the
> v3 dataset documentation and `lerobot >= 0.4`. Check the installed version and
> the current docs before copying code. Pin the version in a separate optional
> dependency group so the core project remains reproducible.

## 2. The v3 dataset format

A LeRobot v3 dataset is file-based, not episode-file-based:

```text
dataset/
├── meta/
│   ├── info.json          # schema: features, shapes, dtypes, fps, path templates
│   ├── stats.json         # global feature statistics
│   ├── tasks.jsonl        # natural-language task descriptions
│   └── episodes/          # per-episode metadata, chunked Parquet
├── data/
│   └── chunk-000/
│       └── file-000.parquet   # many episodes concatenated
└── videos/
    └── chunk-000/
        └── observation.images.top/
            └── file-000.mp4
```

Key ideas:

- **Tabular signals** (state, action, timestamps, indices) live in Parquet.
- **Video** lives in MP4, sharded per camera.
- **Episode boundaries** are reconstructed from metadata offsets, not from file
  names.
- `meta/info.json` is the schema contract: feature names, shapes, dtypes, fps,
  and path templates.
- `meta/stats.json` contains normalization statistics; use them when training on
  a public dataset, or recompute them on your train split.

A sample from `LeRobotDataset` is a dictionary of tensors:

```python
{
    "observation.state": tensor([...]),          # (state_dim,)
    "observation.images.top": tensor([...]),     # (C, H, W) uint8
    "action": tensor([...]),                     # (action_dim,)
    "timestamp": tensor(...),
    "episode_index": tensor(...),
    "frame_index": tensor(...),
    "task_index": tensor(...),
}
```

With `delta_timestamps`, a key becomes a temporal stack:

```python
dataset = LeRobotDataset(
    repo_id,
    delta_timestamps={
        "observation.images.top": [-0.1, 0.0],
        "observation.state": [-0.1, 0.0],
        "action": [0.0, 0.05, 0.10, 0.15],
    },
)
sample["observation.images.top"].shape  # (2, C, H, W)
```

The loader handles padding at episode boundaries according to its own rules.
Read them; do not assume they match your `DemoDataset` sampler.

## 3. Load a public dataset

The PushT dataset is a good first target: 2-D actions, 96×96 images, and a task
that Diffusion Policy was evaluated on.

```python
from lerobot.datasets import LeRobotDataset

ds = LeRobotDataset("lerobot/pusht")
print(ds.meta.features)
print(len(ds), ds.fps)

sample = ds[0]
for key, value in sample.items():
    if hasattr(value, "shape"):
        print(key, tuple(value.shape), value.dtype)
```

To train a policy with temporal context:

```python
delta_timestamps = {
    "observation.image": [-0.1, 0.0],
    "observation.state": [-0.1, 0.0],
    "action": [i * 0.05 for i in range(16)],
}
ds = LeRobotDataset("lerobot/pusht", delta_timestamps=delta_timestamps)
```

Feature names differ across datasets (`observation.image` vs
`observation.images.top`). Print `ds.meta.features` and adapt; do not hard-code a
key from a blog post.

### Adapting a public dataset to this project

Your models expect:

```text
obs["state"]       (T_o, 18)
obs["image"]       (T_o, 96, 96, 3) uint8
action             (T_p, 2)
action_pad         (T_p,)
```

A public dataset will have a different state/action dimension and image key.
Write a thin adapter that:

1. selects the relevant keys;
2. converts image layout `(C,H,W)` to `(H,W,C)` if needed;
3. maps actions to the environment's action range;
4. recomputes normalization statistics on the training split;
5. preserves episode boundaries when building windows.

Do not force a public dataset into the PlanarPush dimensions by truncating or
zero-padding state. Train a separate policy with the correct dimensions, or
change the environment to match the dataset. Silent padding is a bug.

A minimal adapter:

```python
from torch.utils.data import Dataset


class LeRobotWindowDataset(Dataset):
    def __init__(self, ds, obs_horizon=2, action_horizon=16, image_key="observation.image"):
        self.ds = ds
        self.obs_horizon = obs_horizon
        self.action_horizon = action_horizon
        self.image_key = image_key

    def __len__(self):
        return len(self.ds)

    def __getitem__(self, idx):
        sample = self.ds[idx]  # delta_timestamps already applied
        image = sample[self.image_key]
        if image.ndim == 4 and image.shape[1] == 3:  # (T, C, H, W)
            image = image.permute(0, 2, 3, 1)
        return {
            "obs": {
                "state": sample["observation.state"].float(),
                "image": image,
            },
            "action": sample["action"].float(),
        }
```

This is not enough for a serious training run: the public loader's padding,
normalization and episode indexing must be understood. Treat it as a starting
point for exploration, not a drop-in replacement for the validated sampler.

## 4. Export your demonstrations to LeRobot format

If you want your PlanarPush data to be usable by LeRobot tooling, create a
dataset with the v3 API. The exact signature depends on the version; the shape of
the code is:

```python
from lerobot.datasets import LeRobotDataset

features = {
    "observation.state": {"dtype": "float32", "shape": (18,), "names": None},
    "observation.images.top": {
        "dtype": "video", "shape": (96, 96, 3),
        "names": ["height", "width", "channels"],
    },
    "action": {"dtype": "float32", "shape": (2,), "names": None},
}

dataset = LeRobotDataset.create(
    repo_id="your-name/planarpush",
    fps=20,
    features=features,
    root="data/planarpush_lerobot",
)

for episode in episodes:
    for t in range(len(episode["action"])):
        dataset.add_frame({
            "observation.state": episode["state"][t],
            "observation.images.top": episode["image"][t],  # HWC uint8
            "action": episode["action"][t],
            "task": "push the puck to the green goal",
        })
    dataset.save_episode()

dataset.finalize()  # required: flushes Parquet metadata and closes writers
```

Practical notes:

- `finalize()` is mandatory in v3; without it, the Parquet files can be corrupt.
- Video encoding requires ffmpeg (or the codec backend LeRobot uses). Test with a
  single episode before exporting hundreds.
- Image shape conventions differ between “image” and “video” features; check the
  docs for the version you install.
- Add metadata for success/failure; LeRobot's schema may not have a standard
  `success` field, so use a custom feature or a sidecar JSON.
- Do not push to the Hub until you have verified the dataset loads and plays.

Exporting is optional. The HDF5 dataset in this project is already a valid,
documented format; LeRobot compatibility is a convenience, not a requirement.

## 5. From simulation to a real arm

A real SO-101 or similar low-cost arm changes the problem in ways that the
simulation hides.

### Action space

- Simulation: delta joint targets, normalized.
- Real robot: often absolute joint positions or Cartesian poses, with a
  calibrated leader arm.
- Pick one convention, record it, and make the policy output the same thing at
  training and deployment. Most sim-to-real failures are action-space mismatches.

### Timing

- Simulation runs at a fixed 20 Hz.
- A real control loop has variable latency: camera exposure, inference, serial
  communication.
- Measure end-to-end latency and either lower the control rate or predict action
  chunks and execute them open-loop for a few steps.
- Diffusion/ACT inference can be slower than the control period; chunking is not
  only a modelling choice, it is a real-time requirement.

### Calibration

- Camera intrinsics and extrinsics must be calibrated for point clouds.
- Joint zero offsets must be calibrated; a few degrees of offset changes the
  action distribution.
- Use the same camera mounting and resolution at training and deployment.

### Data

- 50–200 human demonstrations is a realistic starting point.
- Human demos are multimodal; this is where CVAE/diffusion policies earn their
  keep.
- Record failures and near-misses; they are useful for evaluation and for
  understanding the data distribution.
- Keep a fixed train/val/test split by episode, not by frame.

### Safety

- Start with low speeds and a clear workspace.
- Add a physical emergency stop and software joint/velocity limits.
- Clamp policy outputs; never let a learned policy command an unbounded action.
- Test the policy with the robot powered but the arm unloaded, then with a soft
  object, before full contact.

### Sim-to-real checklist

- [ ] Same observation keys and dimensions.
- [ ] Same action convention and units.
- [ ] Same camera intrinsics/extrinsics (if using point clouds).
- [ ] Same control rate and action chunk execution.
- [ ] Normalization statistics from real training data, not simulation.
- [ ] Latency measured and accounted for.
- [ ] Domain randomization in simulation (lighting, colours, camera pose,
      object positions) if you train in sim and deploy in real.
- [ ] A safe fallback policy and an emergency stop.

## 6. What to study next

### Better policies

- **Diffusion Transformer / DiT** denoisers.
- **Flow matching** and consistency models for faster sampling.
- **ACT with ResNet18 and multiple cameras**, closer to the original.
- **DP3 with a Point Transformer** or a 3-D backbone such as sparse convents.
- **Vision-language-action** models conditioned on task text.

### Better data

- Human teleoperation datasets (ALOHA, SO-101, RoboMimic).
- DAgger and interactive corrections.
- Synthetic demonstration generation and augmentation.
- Offline RL on demonstrations plus suboptimal data.

### Better evaluation

- Multi-task benchmarks with held-out objects and scenes.
- Robustness to camera pose, lighting and clutter.
- Real-robot success rates with confidence intervals.
- Latency and safety metrics, not just success.

### Theory

- Reward ambiguity and identifiability in IRL.
- Regret bounds for BC and DAgger.
- Occupancy-measure matching and its sample complexity.
- Why diffusion policies can represent multimodal action distributions.

## 7. A realistic capstone

If you want one project that ties everything together:

1. Record 100 human demonstrations on an SO-101 pick-and-place task.
2. Evaluate BC, ACT and Diffusion Policy on 50 held-out initial conditions.
3. Add a colour/lighting shift and a camera-pose shift.
4. Compare image and point-cloud policies (DP vs DP3) using a calibrated depth
   camera.
5. Write a 4-page report with a robustness matrix, failure analysis and a
   reproducible command list.

That is a substantial but achievable portfolio project. The planar benchmark in
this tutorial is the controlled warm-up; the real robot is where the assumptions
break.
